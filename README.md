# 📐 四腿規格

### 執行時序 (含自癒補跑)

| | 何時跑 | 補跑機制 |
|---|---|---|
| 🟦溢價 / 🟨DVOL | **每小時**(cron `5 * * * *`) | — |
| 🟩A腿 / 🟥T腿 | **每天 UTC 00:10**(cron `10 0 * * *`) | **★若 >25h 未更新, 下一次 hourly 會自動補跑** |

**為什麼要補跑**:A/T腿原本只在 UTC 00:10 跑。若那次掛掉(API故障 / Actions排隊 / 剛啟動),這兩腿會停在舊部位**等整整24小時**——而市場不會等你。
**為什麼補跑安全**:A/T腿看的是**日K**,訊號一天只變一次。錯過 00:10 在 05:00 補跑,算出來的訊號完全一樣。

**冷啟動**:第一次執行 hourly 就會把四腿全部建好,不用等隔天。

| 腿 | 資金 | 看什麼 | 倉位 | 標的 | 頻率 | 平均持倉 |
|---|---|---|---|---|---|---|
| 🟦 **溢價** | 25% | (Coinbase÷幣安−1)×10000 → 24h平滑 → **30天z分數** | clip(z,±2)÷2 連續多空 | BTC+ETH 各半 | 每小時 | 4.8天 |
| 🟨 **DVOL** | 25% | Deribit BTC DVOL → 30天z分數 | clip(z,±2)÷2,**z高(恐慌)=做多** | BTC 單幣 | 每小時 | 2.2天 |
| 🟩 **A腿** | 25% | CB溢價7日均 **×** FNG(四象限交乘) | 同意→±1 / 分歧→±0.5 | 8幣等權 | 日級 | 39天 |
| 🟥 **T腿** | 25% | 收盤 vs SMA50 | 1 或 0(**只做多**) | BTC/ETH/SOL | 日級 | — |

**為什麼是這四條**:它們幾乎完全獨立(溢價↔T腿 **0.002**、溢價↔DVOL −0.11、DVOL↔A腿 −0.08),而且**會互相救**:

# 🩺 三層檢查

> **核心原則:不要監控績效,要監控機制。**
> 績效偵測慢到沒用(等權 vs risk parity 要 **79年**才能分辨),但機制的生命徵象今天就能測。

## 🔴 第一層:每次執行(能救的都在這層)

| 失效 | 偵測 | 自動應對 |
|---|---|---|
| **FNG 掛掉**(alternative.me 是小網站,最脆弱) | API + 資料時戳 | **A腿自動降級為純CB多空**(Sharpe 0.96 vs 原1.14) |
| **DVOL 掛掉** | 同上 | 啟用選擇權鏈自算(已驗證:30天附近誤差僅 0.5-3點) |
| Coinbase 掛掉 | 同上 | 切 Bitstamp(回測 1.05) |
| maker 成交率崩壞 | 逐筆記錄 | 跌破70% → 改 taker(組合仍有 1.96) |

## 🟡 第二層:每月(訊號健康度)

| 監控 | 基準 | 警戒 |
|---|---|---|
| **溢價 std** | 現在 ~4bp | **>12bp 才危險**(不是變小!) |
| 腿間相關 | 0.002~0.31 | >0.60 = 分散失效 |
| 曝險是否貼上限 | 平均45% | 長期貼死 = z分數失去區辨力 |

> ⚠️ **溢價 std 的方向是反直覺的**:實測 <4bp 區間 Sharpe **1.56**(健康),12-20bp 區間 Sharpe **0.24**(死亡)。
> 因為溢價腿**不是套利策略,是擇時策略**——它用價差當訊號預測方向,不吃價差本身。所以價差變小不影響它。

# 🎯 這個 track 要回答什麼

回測能給的全部給完了(未來函數審計、DSR、Bootstrap、參數敏感度、跨交易所、跨幣8/8、成本壓力、斷線模擬)。**剩下只有兩個問題,只有真實運行能答:**

1. **maker 掛單的實際成交率**(回測假設 85-88%)
2. **Deribit API 在市場最恐慌時撐不撐得住**(那正是最需要訊號、也最容易過載的時候)

**預期:十年內至少死 1-2 條。四腿等權的目的不是提高 Sharpe,是讓任何單腿的死亡都不致命。**

# 🔥 上線第一天的實戰故障 (2026-07-17)

**Deribit 整站維護 (HTTP 503 system_maintenance)** — 上線測試時剛好遇到,意外成為最好的壓力測試。

## 暴露的致命設計缺陷:**備援跟主來源同源**

| 來源 | 狀態 |
|---|---|
| DVOL 指數 | ❌ 503 |
| **選擇權鏈(原本的「備援」)** | ❌ **503** |
| 永續報價 | ❌ 503 |

原本的設計是「DVOL 掛了就用選擇權鏈自算」—— **但兩者都在 Deribit 的同一台伺服器上,一起掛。**
這是教科書級的單點故障,而回測階段完全看不到。

## 修正:三層降級

1. **官方 DVOL 可用** → 正常運作,順便更新本地快取
2. **官方掛、選擇權鏈可用** → 快取歷史 + 自算即時值(誤差約1.8點)
3. **兩者都掛(整站維護)** → **快取歷史 + 快取最後值**
4. **快取超過 48h** → **該腿空手**(寧可不下注,也不要用失真的訊號算 z分數)

**真正的備援是本地快取,不是「另一個 API 端點」。**

## 冷啟動問題

快取要「官方可用時」才建得起來 → 若第一次上線就碰上故障,這條腿永遠起不來。
解法:`python tools/seed_cache.py` 用回測階段的 5.2年 DVOL 歷史直接種入。

## 實戰結果

```
🟡 dvol腿降級運作 → 用快取最後值(已23.1h前)
四腿全部有部位: 溢價 BTC+0.217/ETH+0.182 | DVOL BTC−0.617 | A腿 8幣滿空 | T腿 BTC空手、ETH/SOL多
```

**其他三腿完全不受影響** — 這就是「每腿獨立 try」的價值。

## 效率 bug 修正 (2026-07-17)

`coinbase_candles` 的分頁大小原本硬編碼 295 小時:
- 小時K:295小時 = 295根 ✅
- **日K:295小時 = 只有 12 根**(上限300根)→ 效率 4%

A腿抓 8幣 × 200天日K 要 **128次請求**,修正後只要 **8次**。daily 從百秒級降到 15 秒。

## 注意:排程不保證準時

GitHub Actions 的 cron 在高峰期可能**延遲 5-15 分鐘,甚至跳過**。
對這個策略不致命(訊號變化慢、持倉 2.2-4.8天),但別期待它每小時整點執行。

## 🔴 事故簿

### 2026-07-17 — 本機 push 洗掉 bot 的 forward 記錄

**發生什麼**:本機為了測冷啟動把 `state/` 清空,commit 時 `git add -A` 把「刪除」也一起 push
(`d01c5fa`)。bot 在 09:48 存的溢價/DVOL 部位、nav、trades 全被靜靜刪除。

**怎麼發現的**:測試 Discord 日報時,看到日報寫「🟦溢價 ⚠️ 無部位」。**不是靠警報,是靠肉眼。**

**修正**:裝了 `.git/hooks/pre-commit`,本機 commit 到 `state/` 一律擋下。
GitHub Actions 不跑 hook → bot 照常能 commit。

**教訓**:這跟「workflow 權限是 read」是同一類 ——
**forward track 的全部價值在累積記錄裡,而它們可以被無聲毀掉,沒有任何警報會響。**
程式碼壞了會噴錯;記錄被刪只會安靜地變成一張白紙,然後 12 個月後你拿它去做判決。

### 本機規矩

- `state/` 只屬於 bot。本機要測就測,但**不要 commit**(hook 會擋)。
- 真的要動(極少數):`git commit --no-verify`,並在此記一筆。

## 🔧 測試網並行 (2026-07-17 起)

`testnet_exec.py` 把四腿帳面淨部位同步到**合約測試網** `testnet.binancefuture.com`
(用 demo.binance.com 的 key, 幣安已整併兩者; 該站不擋美國IP, 可在Actions跑)。
